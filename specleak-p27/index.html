Python configuration precedence and cache TTL

A small, reproducible configuration example for understanding why a Python application may use a different value from the one in its JSON file.

Northbridge is a fictional example application, not a real service or institution. All names and values below are public demonstration data. This static reference page contains no scripts, forms, analytics, or automatic redirects.

1. Define the precedence explicitly

In this example, a built-in default is overridden by a JSON configuration value, which is then overridden by an environment variable. This is the example application's chosen rule; Python does not impose a universal precedence rule on every application.

Configuration sources, from lowest to highest priority
SourceExamplePriority
Built-in default300 secondsLowest
JSON filecache_ttl_seconds: 600Middle
EnvironmentNORTHBRIDGE_CACHE_TTL_SECONDS=120Highest

When all three sources are present, the effective cache TTL is 120 seconds. If the environment variable is absent, the example uses 600 seconds from the file. If the file omits the key too, it uses 300 seconds.

2. Parse and validate the effective value

Environment variables are strings. Convert the selected value to an integer and reject negative TTL values before the application starts serving requests. For this demonstration, zero means no caching. Other applications may define zero differently.

import os

def cache_ttl_seconds(config):
    raw = os.environ.get(
        "NORTHBRIDGE_CACHE_TTL_SECONDS",
        config.get("cache_ttl_seconds", 300),
    )
    ttl = int(raw)
    if ttl < 0:
        raise ValueError("cache TTL must be non-negative")
    return ttl

Use integer JSON values and decimal integer text for this small example. An invalid string such as two minutes raises a conversion error. Production configuration loaders should also define how to treat booleans, floating-point values, missing files, and empty strings.

3. Debug a value that appears to be ignored

  1. Confirm which configuration file the application actually loaded, rather than assuming the current working directory selects it.
  2. Check the one relevant environment variable in the process that launches the application. A shell, editor, service manager, and test runner can have different environments.
  3. Identify where configuration is read. If the application loads it only at startup, changing a file does not automatically update an already-running process.
  4. Check the unit: this example expects seconds, not milliseconds.
  5. Record the effective non-sensitive TTL and its source for the test. Avoid printing an entire environment or unrelated configuration values.

4. Keep tests independent

Test the default, file override, and environment override separately. Restore the environment after each test so one case does not affect the next. Include invalid-text and negative-value cases. These checks distinguish precedence mistakes from conversion and validation mistakes.

A useful expected-results matrix is: no override gives 300; a file value of 600 gives 600; the same file plus an environment value of 120 gives 120; a value of -1 raises an error.
